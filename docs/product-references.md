# 产品设计参考

## 参考原则

PixPin 和 Listary 是 Tbox 的优先参考对象。所有交互、布局和内容解决方案，都应先查阅这些优秀工具已有的成熟方案，再决定 Tbox 的实现方式，避免在已有优秀方案时重复设计。

本原则适用于新增功能、现有功能优化、界面重构，以及按钮、工具栏、设置、提示和帮助内容等细节，不限于下表列举的场景。

## 优先参考对象

| 工具 | 官方参考入口 | 重点参考场景 |
| --- | --- | --- |
| PixPin | [快速上手](https://pixpin.cn/docs/getting-started/quick-start) | 截图、贴图、标注、长截图、录屏、文字识别的操作流程；选区与工具栏布局；快捷键提示、结果窗口和帮助内容的组织。 |
| Listary | [官方网站](https://www.listary.com/) | 文件查找、文件夹跳转、打开与保存对话框协作；搜索框、结果列表、常用目录入口的布局；键盘操作和即时反馈。 |

上表说明参考方向，不表示将参考工具的全部功能纳入 Tbox。涉及具体功能时，应继续查阅对应的官方文档或实际交互，而不是只依据首页介绍推断细节。

## 设计与开发时如何使用

1. **先查已有方案**：明确当前要解决的用户问题，优先查看 PixPin、Listary 中相近场景的交互、布局和内容组织；截图类场景优先看 PixPin，文件导航类场景优先看 Listary，通用场景可对照两者。
2. **优先沿用成熟模式**：已有方案适用时，优先采用其操作路径、信息层级、动作分组及反馈方式，不无故另造一套。
3. **结合 Tbox 适配**：保留 Tbox 的统一品牌、设计规范和 Windows / macOS 共用交互，并按目标平台惯例适配快捷键、权限和系统窗口协作。参考不等于直接复制品牌、图标、文案或其他受保护资源。
4. **说明差异**：设计说明或 PR 中注明参考工具、具体页面或操作，以及采用的模式；如不采用已有方案，说明不适用的原因和替代方案。
5. **不自动变更已确认需求**：参考工具的功能和行为不直接成为 Tbox 的需求。与现有已确认规则冲突时，先明确差异，按需求变更流程更新，不因“参考”静默改变行为或扩大功能范围。

## 固定执行顺序

后续每项交互、布局或内容设计工作，必须按“竞品寻找方案 → 收集证据 → 对照 Tbox → 适配设计 → 验证”的顺序推进，不能先自行设计，再补上竞品名称作为背书。

1. 在 PixPin、Listary 中寻找相同或相近问题的现成解决方案，记录具体页面、场景和查阅日期；未找到时明确说明，不捏造对应能力。
2. 收集相关界面和流程证据，区分客户端实测截图、官方展示图、官方文档示意图及文字说明。记录来源、版本（未知则标记未知）和状态，不用静态图片证明实际响应速度或跨平台兼容性。
3. 对照 Tbox 当前需求、实现和可用验证证据，区分“已有且可保留”“已有但难发现或反馈不足”“尚未实现”“明确不在范围内”，避免将已有能力误列为缺失。
4. 提出融入 Tbox 的方案，说明借鉴点、保留或调整的部分、优先级和可验证的验收方式；不整套照搬竞品界面，也不为功能数量而扩大范围。
5. 临时收集的图像、来源清单、对照图和待确认优化建议放在 Git 忽略的 `TEMP/`，经用户认可后再整理到正式文档或资源目录。引用材料保留来源与权利归属，不把收集视为获得再分发许可。
6. 用户确认涉及产品行为的方案后，更新产品需求、实施并验证；未实施的优化建议不得标记为已完成。

## 文档分工与验收

- [产品需求](product-requirements.md) 是产品行为和验收标准的唯一活文档；本文件记录参考对象及使用原则。
- [UI 设计规范](ui-design-system.md) 记录 Tbox 已确认的视觉与组件规则；参考方案在该规范下适配。
- 后续设计与开发验收时，检查是否优先查阅了相关参考方案、是否说明采用或偏离的理由，以及是否保留已确认的产品规则和跨平台一致性。
